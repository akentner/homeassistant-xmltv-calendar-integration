  <decision>How the config entry unique_id identifies a source (SRC-13 duplicate rejection)</decision>
  <context>The unique_id is written into .storage/core.config_entries on every installation. Changing the scheme after release needs an async_migrate_entry plus a VERSION bump that rewrites every existing entry. EPG URLs often carry API keys in the query string. entry.data stores the URL either way, but the unique_id is also copied into diagnostics and entity-registry lookups. Both options use the same normalization: yarl lower-cases scheme and host, drops the default port, the fragment and dot segments, and keeps the query. File paths go through os.path.realpath. Both prefix the source type ("url:" / "file:").</context>
  <options>
    <option id="sha256">
      <name>SHA-256 hex of "type:normalized" (recommended by RESEARCH)</name>
      <pros>Keeps API keys out of a second persisted field and out of later diagnostics (Phase 3); fixed 64-character length; still detects duplicates exactly</pros>
      <cons>Not human-readable in .storage; debugging means recomputing the hash</cons>
    </option>
    <option id="plain">
      <name>Plain "type:normalized" string</name>
      <pros>Readable in .storage and diagnostics; trivially debuggable</pros>
      <cons>Duplicates any token from the URL query into the unique_id; diagnostics redaction (Phase 3) must then cover unique_id too; switching to a hash later needs a migration</cons>
    </option>
  </options>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-22 | Denial of service | async_probe_url in the flow | medium | mitigate | Reads at most PROBE_BYTES (64 KiB) with DOWNLOAD_TIMEOUT, then releases the connection; the full download happens in setup, not in the flow |
| T-01-SC | Tampering | uv dev installs | high | mitigate | No new packages in this plan |
