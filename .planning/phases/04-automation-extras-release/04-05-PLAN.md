## Phase Goal

**As a** Home Assistant user with filtered XMLTV calendars, **I want to** automate around matches beyond plain calendar triggers (next-match sensor, new-match event, recent past matches, ready-made blueprint) and install a documented, bilingual, tagged release via HACS, **so that** I can act on the programmes I care about without hand-built polling automations and keep the integration up to date.

<objective>
Add the "Last fetch" diagnostic sensor (new requirement AUT-06, D-20..D-25): one per calendar device, disabled by default, showing when the source last ran a refresh, what started it, what happened (HTTP status, cache handling, sent validators) and what came out, persisted across restarts and mirrored in diagnostics.

Purpose: the user's test calendar went days without updating; this sensor shows straight from the device page whether the schedule fires and what the server answered.
Output: RefreshAttempt record and persistence, run recording in the coordinator, HTTP status plumbing in source.py, LastFetchSensor, diagnostics last_attempt, translations, AUT-06 bookkeeping, tests.
</objective>

## Interpretation note (D-21 vs D-23)

D-21 counts the start from the disk cache as a run, and D-23 asks that the sensor show the last real run after a restart. Both hold as follows: the cache start is recorded as its own run (trigger startup, outcome cache_start), so the user sees that HA restarted and whether the schedule fires afterwards; the persisted record is what diagnostics show while the entry is not loaded; and last_success (persisted health) keeps the time of the last successful download across restarts. If the UAT shows the user wants the pre-restart download details on the sensor after a restart, that is a follow-up change to how a cache start is recorded.
