<objective>
Wire the engine's local-time variables through every Home Assistant call site and lock the runtime behavior of templates with regression tests: local `start` and `end` everywhere, one WARNING per calendar for runtime failures, and no side effects of template edits on matches.

Purpose: D-05 (start and end as local datetimes), D-03 at the entity level, D-08 for hand-edited storage, and the CONTEXT requirement that a template edit must not re-announce matches. 05-01 created the `tz` parameter and the warn-once holder; this plan is where the callers use them.
Output: zone threading in `calendar.py`, `matcher.py` and `preview.py`, and `tests/test_template_runtime.py`.
</objective>

| Calendar entity to automations | Template edits must not change event identity or announcements |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-13 | Information disclosure | WARNING content when a stored template fails | medium | mitigate | warnings carry the calendar name and the exception type or reason key only; tests assert no programme title or template text appears in the log, for both runtime failures and unusable stored templates |
| T-05-14 | Tampering | a template edit re-announcing matches or changing UIDs and so double-firing user automations | medium | mitigate | UIDs hash the raw programme title and the match store keys on UIDs; regression tests assert no new-match event, identical UIDs and an identical seen-set after a template edit |
| T-05-15 | Denial of service | per-event rendering on the event loop | low | mitigate | templates are precompiled once per calendar, rendering costs microseconds per event (RESEARCH measured 5.5 microseconds), slices over 200 programmes already build in the executor, and the zone is resolved once per call |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | no packages added |
</threat_model>
