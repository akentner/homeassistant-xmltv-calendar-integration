## Phase Goal

**As a** Home Assistant user with XMLTV sources, **I want to** have each source cached across restarts, refreshed on my own schedule and only when the feed changed, tolerant of failures and timezone quirks, editable later, and visible when something goes wrong, **so that** every calendar stays populated at minimal network and CPU cost.

(Story text reused verbatim from 03-01..03-08.)

Gaps closed by this plan: 03-VERIFICATION.md `gaps[0]` (CR-01, 03-01 truth 1 and the 03-01 prohibition) and `gaps[1]` (CR-02, 03-04 truths 3 and 8, roadmap SC 4). Both have one root cause: the refresh target is only updated on the anticipated paths, and the next target is derived from a `utcnow()` that may lie just before the target being served. Both live in `_async_update_data` / `_set_regular_target`, so they are fixed in one plan.

<objective>
TDD gap closure for CR-01 and CR-02 in `coordinator.py`.

1. CR-01: Home Assistant arms the coordinator timer at `int(loop.time()) + self._microsecond + interval` (update_coordinator.py:283, `_microsecond` 0.05..0.5 s), so a refresh can fire up to ~0.95 s before `_next_refresh_at`. `_set_regular_target` then computes `next_slot(now)`, which is the slot still less than 1 s ahead, `_schedule_refresh` clamps it to `MIN_DELAY`, and the feed is requested a second time. A fast failure at that moment gets a 1 s backoff instead of 5 min. Fix: a pure `refresh_base(now, target)` in `xmltv/schedule.py` returns the target when it lies at most `EARLY_FIRE_TOLERANCE` (2 s) ahead, and both the success and the failure target are computed from that base. A plain `max(now, target)` is NOT used, because it would let a manual `update_entity` hours before the slot consume the slot (daily) or push the interval out (interval).
2. CR-02: only `UpdateFailed` is handled. Any other exception reaches HA's generic handler, which re-arms the timer with the target just served (now in the past), so the source is downloaded about once per second, never recorded, never backed off and never reported in Repairs. Fix: one failure handler for `UpdateFailed` and every other `Exception` (cancellation is not an `Exception` and passes through), covering the cache start, the download and the parse; unexpected exceptions are recorded with reason `unable_to_fetch`, back off, and are re-raised as `UpdateFailed`.

Purpose: restores "minimal network cost" and "tolerant of failures" from the phase goal: one request per slot, and a polite, visible backoff whatever goes wrong.
Output: `EARLY_FIRE_TOLERANCE` and `refresh_base` in schedule.py, a restructured `_async_update_data` with `_async_read_source` and `_async_handle_failure`, and regression tests at the pure, scheduled-refresh and Repairs levels.
</objective>

## Planner Decisions (Claude's discretion, all reversible)

- **Served-target base instead of `max(now, target)`.** The review and the verifier suggest `max(now, _next_refresh_at)`. Applied literally it breaks D-12: a manual `update_entity` at 10:00 would set the base to today's 18:15 slot and skip it, and in interval mode it would push the next refresh to target + interval. `refresh_base` keeps the verifier's intent ("the served target") by treating only a target at most `EARLY_FIRE_TOLERANCE` ahead as served. Two guard tests pin this.
- **Tolerance 2 s.** HA's early fire is bounded by ~0.95 s (`int(loop.time())` truncation minus the 0.05-0.5 s offset). 2 s gives headroom for clock-read skew; a manual refresh within 2 s before a target counts as serving it, which changes nothing a user can notice. Rating: reversible (one constant, no stored contract).
- **Cache start inside the guarded region.** The gap names "the fetch/parse"; parsing the cached payload at setup is the same parse, and without the guard a MemoryError there would keep a source in SETUP_RETRY forever without ever raising a Repairs issue. Rating: reversible.
- **Logging.** RESEARCH Pitfall 8 keeps anticipated failures at DEBUG because HA logs UpdateFailed once per streak. An unexpected exception is a bug signal, so it gets one content-free WARNING per failed attempt (throttled by the backoff), plus the traceback at DEBUG.
